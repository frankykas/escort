# Pre-Beta Automated Audit

Generated by static analysis of the codebase before exposing the platform
to closed beta testers. Findings are graded by severity:

- 🔴 **Critical** — fix before any external user touches the app
- 🟠 **High** — fix before beta opens
- 🟡 **Medium** — fix during beta
- 🟢 **Pass** — verified clean, no action needed

---

## Headline finding

🔴 **Every mutating API route trusts a `userId` sent in the request body.**
There is no server-side verification that the caller actually owns that
user account. This is the single most important issue in the audit.

Concrete impact: any visitor with the public Supabase URL can hit
`/api/listings/bump` with someone else's `providerId` and burn that
provider's credits. They can post as someone else, send messages as someone
else, accept message requests on someone else's behalf, and so on.

This pattern is used by **every non-admin route** that mutates data:
`/api/listings/*`, `/api/posts`, `/api/chat/*`, `/api/block`,
`/api/notifications`, `/api/push/*`, `/api/persona/complete`,
`/api/listings/bump`, `/api/listings/relist`.

**Fix.** Replace the `userId`-from-body pattern with a session check. Two
options:

1. Switch these routes to a cookie-aware Supabase client
   (`createServerClient` from `@supabase/ssr` with cookie wiring) and call
   `supabase.auth.getUser()` to derive the userId from the verified
   session. Reject if it doesn't match the body.
2. Or accept the body `userId` as a hint, but assert it equals the session
   user before proceeding.

Either way, the change is mechanical and contained — every route follows
the same template, so you can do all 22 in one pass.

This must ship before the beta opens. With a closed friend group it's
unlikely to be exploited, but the moment a single tester shares a link
publicly, you have a problem.

### 🟠 4. Notification spam vector

🟠 **`notifications: system insert` policy uses `WITH CHECK (true)`** at
[supabase/migrations/016_notifications.sql:69](supabase/migrations/016_notifications.sql#L69).

This means any authenticated user can directly insert a notification row
targeting any other user. With the Supabase JS client, a malicious tester
could spam notifications to anyone in the database.

**Fix.** Restrict to service role only:

```sql
CREATE POLICY "notifications: service insert"
  ON notifications FOR INSERT
  WITH CHECK (auth.role() = 'service_role');
```

The DB triggers that create notifications already run as the table owner,
so they bypass RLS and won't be affected.

### 🟡 6. API error handling — partial coverage

22 of 28 API routes have **no `try/catch` block at all**. They check
`if (error)` after Supabase calls (which is the main happy path) but a
malformed request body that fails `await req.json()`, or any other
unexpected throw, will surface as a 500 with no useful message.

Files lacking outer try/catch:
- [app/api/admin/auth/route.ts](app/api/admin/auth/route.ts)
- [app/api/admin/credits/route.ts](app/api/admin/credits/route.ts)
- [app/api/admin/dashboard/route.ts](app/api/admin/dashboard/route.ts)
- [app/api/admin/packages/route.ts](app/api/admin/packages/route.ts)
- [app/api/admin/reports/route.ts](app/api/admin/reports/route.ts)
- [app/api/admin/settings/route.ts](app/api/admin/settings/route.ts)
- [app/api/admin/suspend/route.ts](app/api/admin/suspend/route.ts)
- [app/api/admin/verification/route.ts](app/api/admin/verification/route.ts)
- [app/api/analytics/route.ts](app/api/analytics/route.ts)
- [app/api/block/route.ts](app/api/block/route.ts)
- [app/api/chat/mark-read/route.ts](app/api/chat/mark-read/route.ts)
- [app/api/chat/messages/route.ts](app/api/chat/messages/route.ts)
- [app/api/geo/route.ts](app/api/geo/route.ts)
- [app/api/listings/bump/route.ts](app/api/listings/bump/route.ts)
- [app/api/listings/relist/route.ts](app/api/listings/relist/route.ts)
- [app/api/listings/route.ts](app/api/listings/route.ts)
- [app/api/notifications/route.ts](app/api/notifications/route.ts)
- [app/api/packages/checkout/route.ts](app/api/packages/checkout/route.ts)
- [app/api/packages/route.ts](app/api/packages/route.ts)
- [app/api/persona/complete/route.ts](app/api/persona/complete/route.ts)
- [app/api/push/subscribe/route.ts](app/api/push/subscribe/route.ts)
- [app/api/push/unsubscribe/route.ts](app/api/push/unsubscribe/route.ts)

**Fix.** Wrap each handler body in `try { ... } catch (err) { return
NextResponse.json({ error: "Internal error" }, { status: 500 }); }` and
log `err` server-side. This is a 5-minute mechanical change you can pair
with the auth fix.

### 🟢 8. Form validation — covered

The two highest-stakes forms (signup and password reset) both validate
client-side before submitting:

- [app/auth/signup/page.tsx:28-43](app/auth/signup/page.tsx#L28-L43) checks
  age confirmation, terms acceptance, password match, and minimum
  password length (8 chars).
- [app/auth/update-password/page.tsx:26](app/auth/update-password/page.tsx#L26)
  checks minimum password length.

Email is validated by `type="email"` on the input. Supabase Auth itself
enforces strong password policies if you turn them on in the dashboard
(recommended — set min length to 10 and require a mix of cases/numbers).

## Recommended order before beta

1. **Fix #5 (API auth gap).** This is the single must-do. ~2 hours of
   mechanical work across 22 routes once the pattern is established.
2. **Fix #4 (notifications policy).** One migration, one line. 5 minutes.
3. **Fix #6 (try/catch wrappers).** Optional but cheap insurance against
   tester confusion when something blows up unexpectedly.

Once those are done, the codebase is clean enough to put in front of real
people. Everything else in the audit came back green.
